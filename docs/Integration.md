# WebmasterID iOS integration

The authoritative guide. Every Swift block below is either copied from the
compiled example at [`Examples/QuickStart`](../Examples/QuickStart) or generated by
`buildMobileSdkIntegration`, whose symbols are checked against the SDK sources
by a test. Nothing here is pseudocode.

> **No real identifiers appear in this document.** `ap_xxxxxxxxxxxxxxxx` and
> `<your-account-key>` are placeholders. A real value in a guide becomes a real
> value in every project that copies it.

---

## 1. Add the package in Xcode

**File → Add Package Dependencies…**, then paste the repository URL:

```
https://github.com/PetroTitan/PetroTitan-webmasterid-swift.git
```

Choose the `WebmasterID` library product.

> The recommended version is **`1.0.1`**. `1.0.0` is also published and its
> SDK code is identical, but its release verification was not deterministic —
> see [`CHANGELOG.md`](../CHANGELOG.md).

In `Package.swift`:

```swift
dependencies: [
    .package(url: "https://github.com/PetroTitan/PetroTitan-webmasterid-swift.git", from: "1.0.1")
],
targets: [
    .target(
        name: "MyApp",
        dependencies: [.product(name: "WebmasterID", package: "petrotitan-webmasterid-swift")]
    )
]
```

> The package identity is `webmasterid` — SwiftPM derives it from the URL's
> last path component, not from the manifest's `name`. (A *path* dependency is
> identified by its directory name instead, which is why the in-repo example
> passes `.package(name:path:)`.)

**Minimum iOS 15. Swift tools 6.0, strict concurrency. No third-party
dependencies.**

## 2. Create the client

```swift
import WebmasterID

let client = WebmasterIDClient(
    configuration: try WebmasterIDConfiguration(
        appPropertyID: "ap_xxxxxxxxxxxxxxxx",
        consent: .notDetermined
    )
)
```

### The app property id is public

It ships inside your binary, and anyone who downloads your app can read it out.
It **addresses** your property; it does not authenticate anything. WebmasterID
treats it that way deliberately — an unknown property and an archived one get
byte-identical answers, so holding an id proves nothing.

**Never put a WebmasterID server key in an app.** There is no configuration
field for one, and there will not be.

There is no shared singleton. Create one client, or several; tests create
their own.

---

## 3. Consent

Three states, mirroring the server exactly. The SDK starts at
`.notDetermined`, which collects **nothing**.

```swift
await client.setConsent(.analyticsAllowed)  // events + pseudonymous identifiers
await client.setConsent(.restricted)        // events only, no stable identifiers
await client.setConsent(.disabled)          // stop, and delete what was kept
```

**Before valid consent:** no event is queued, none is written to disk, none is
sent, and no persistent identifier is created. Consent is checked *before queue
insertion*, not merely before the network — "we never uploaded it" is not the
same statement as "we never collected it".

**`.disabled` deletes.** The queue is emptied, the installation identifier is
forgotten, and the stored account key is removed from the Keychain. It is not
a mute button.

**`.restricted`** sends events with no `installation_id` and no
`external_user_id`, and retains neither.

## 4. SwiftUI lifecycle

The SDK observes nothing on its own and performs no method swizzling, so your
app forwards the lifecycle. That is why there is no automatic screen tracking.

```swift
import SwiftUI
import WebmasterID

struct RootView: View {
    let client: WebmasterIDClient
    @Environment(\.scenePhase) private var scenePhase

    var body: some View {
        ContentView()
            .onChange(of: scenePhase) { phase in
                Task {
                    switch phase {
                    case .active:     await client.applicationDidBecomeActive()
                    case .background: await client.applicationDidEnterBackground()
                    default: break
                    }
                }
            }
    }
}
```

## 5. UIKit / AppDelegate lifecycle

```swift
import UIKit
import WebmasterID

final class AppDelegate: UIResponder, UIApplicationDelegate {
    let client: WebmasterIDClient = /* created once at launch */

    func applicationDidBecomeActive(_ application: UIApplication) {
        Task { await client.applicationDidBecomeActive() }
    }

    func applicationDidEnterBackground(_ application: UIApplication) {
        Task { await client.applicationDidEnterBackground() }
    }
}
```

## 6. Identify after login

```swift
try await client.identify(externalUserID: "<your-account-key>")
```

Pass **your** opaque account key. An email address, a phone number, or anything
containing `@` or whitespace is **refused, not hashed** — hashing a direct
identifier we should never have received would hide the mistake from you.

The raw key is stored in the **Keychain**, never in the on-disk event queue.
Queued events carry an opaque epoch and the value is attached at send time.

## 7. Reset on logout or account switch

```swift
await client.resetIdentity()
```

The account key is forgotten and a new pseudonymous identity begins. Events
queued while the previous user was signed in are delivered **without** their
account key — that loses an attribution, and it is the correct trade.

---

## 8. Track an event

```swift
try await client.track(.appOpen)
try await client.track(.screenView, context: .init(screen: "BookingDetail"))
try await client.track(.ctaTap, context: .init(screen: "BookingDetail", ctaID: "book_now"))
```

Event names are a **closed enum**. There is no free-text name and no
`[String: Any]` metadata bag.

> ⚠ **Never encode sensitive information into a screen, cta or filter
> identifier.** `screen: "diagnosis_knee_arthritis"` is a health fact in a
> field designed for a symbol. The SDK validates the *shape*; it cannot know
> what a string means.

## 9. Flush

```swift
await client.flush()
```

Delivers what is queued, in batches, now. It does not block, it does not
guarantee delivery, and anything undelivered stays on disk.

## 10. Offline queue and retry

| Situation | Behaviour |
| --- | --- |
| No network | Events persist to disk **before** the first attempt |
| Retry | The same `client_event_id` and the **original** occurrence time |
| Duplicate | The server deduplicates on `(app_property_id, client_event_id)`; a duplicate acknowledgement is a success |
| Batch too large | Split deterministically, measured in **UTF-8 bytes** |
| One event too large alone | Dropped locally and counted — never retried forever |
| 429 | `Retry-After` is honoured |
| 5xx / network error | Exponential backoff with bounded full jitter, capped attempts |
| 400 | Permanent — not retried, counted as `permanentlyRejected` |
| Cancellation | Unacknowledged events are preserved |

## 11. App relaunch

The queue is durable and survives termination. On the next launch, undelivered
events are re-offered under their original ids, and the server collapses any
that already arrived. A crash mid-write leaves the previous queue intact: the
file is replaced atomically.

A corrupted queue file is **survived, not crashed on** — the queue starts
empty, `diagnostics().recoveredFromCorruptQueue` records it, and your app keeps
running.

## 12. Diagnostics and troubleshooting

```swift
let d = await client.diagnostics()
d.queuedEvents            // how much is waiting
d.queuedBytes             // encoded size
d.lastStatusCategory      // .success / .rateLimited / .refused / .serverError / …
d.retryState              // .idle / .scheduled(inSeconds:attempt:) / .stopped(reason:)
d.acknowledged, d.deduplicated, d.permanentlyRejected
d.droppedOversized, d.droppedExpired, d.droppedForCapacity
```

Diagnostics contain **no payloads, no event names, no identifiers, no URLs and
no response bodies**. Assume anything here reaches a screenshot, a bug report
and a crash reporter — because it will.

`.stopped(reason: .propertyNotAccepting)` means the server will not take events
for this property. It deliberately does **not** distinguish archived from
unknown.

## 13. Confirming delivery in WebmasterID

1. `diagnostics().acknowledged` rising means the server answered 200.
2. `deduplicated` rising is also success — the server already had those events.
3. `.stopped(reason: .propertyNotAccepting)` means the property id is wrong or
   the property is archived. Check it in **Settings → Mobile apps**.
4. `queuedEvents` staying high with `lastStatusCategory == .serverError` is a
   transport or ingest problem, not a client one.

---

## 14. Apps with no website

An app property does **not** require a related site. An app-only product is a
first-class case: nothing in the SDK sends a site id, a URL or a domain, and
`related_site_id` stays null.

## 15. Limitations, stated plainly

- **No guaranteed background delivery.** iOS gives a backgrounding app a short,
  unguaranteed window. A request started there may not finish. Undelivered
  events are retried on the next launch — that is the guarantee. A background
  `URLSession` would change it and is not implemented.
- **No StoreKit verification, no trusted revenue.** M4 and M5 send analytics
  events. Purchases, subscriptions and refunds are later phases with their own
  verification design, and the server refuses those fields today.
- **No automatic registration inference.** A signup is an event your app
  reports; the SDK does not guess one from a screen or a tap.
- **No region or city.** Country is derived **server-side** from trusted edge
  headers. Region and city are not collected at all.
- **No arbitrary metadata.** There is no dictionary to put it in.
- **No IDFA, IDFV, AppTrackingTransparency, Location Services or
  fingerprinting.** Not disabled — absent.

## 16. Privacy manifest

The package ships `PrivacyInfo.xcprivacy` as a resource. `NSPrivacyTracking` is
`false`, there are no tracking domains, and `NSPrivacyAccessedAPITypes` is
**empty** — audited API by API, not assumed. Collected-data types are declared
as Product Interaction, Device ID (the app-local random installation id), User
ID (your account key) and Coarse Location (the server-derived country); the
reasoning for each, including the arguable one, is written in the file itself.

## In-app purchases (`WebmasterIDStoreKit`)

> **⚠ NOT IN A PUBLISHED RELEASE YET.** This product is on `main` and is planned
> for 1.1.0, which has not been tagged. `from: "1.0.1"` will not resolve it.

### Add the product

```swift
.target(
    name: "MyApp",
    dependencies: [
        .product(name: "WebmasterID", package: "petrotitan-webmasterid-swift"),
        .product(name: "WebmasterIDStoreKit", package: "petrotitan-webmasterid-swift"),
    ]
)
```

Add the second product **only if your app sells something.** `WebmasterID` does
not depend on it and does not import StoreKit, so an app that adds only the core
never links StoreKit and never has to account for it in App Store review.

### Start it

```swift
// ONE client owns consent and identity. The collector is built FROM it.
let analytics = WebmasterIDClient(
    configuration: try WebmasterIDConfiguration(appPropertyID: "ap_…")
)
let storeKit = try await WebmasterIDStoreKit.attached(to: analytics)
await storeKit.start()

// Consent and identity are set on the ANALYTICS client. StoreKit follows,
// immediately — there is no second place to keep them in sync.
await analytics.setConsent(.analyticsAllowed)
try await analytics.identify(externalUserID: currentUser.accountKey)
```

⚠ There is deliberately no `consent` or `externalUserID` on the StoreKit
configuration. Two objects with independent opinions about who the user is will
eventually disagree, and the purchase is the record that gets it wrong.

`start()` opens **one** `Transaction.updates` listener and is safe to call
twice — a second call is a no-op, not a crash and not a second listener.

### Submit the purchase you just made

```swift
let result = try await product.purchase()
if case let .success(verification) = result {
    await storeKit.submit(verification)

    // ⚠ YOU finish it. This SDK never will.
    if case let .verified(transaction) = verification {
        await grantEntitlement(for: transaction)
        await transaction.finish()
    }
}
```

Only `.verified` results are queued and sent. An `.unverified` result means
StoreKit itself could not vouch for the payload on this device; it is counted in
diagnostics and nothing is transmitted. **That is not a substitute for server
verification** — every submitted JWS is still verified against Apple's root
certificates on the server. The local check narrows what is sent; it never
decides what is trusted.

`Transaction.updates` does not deliver the transaction a direct `purchase()`
call returns in the same session, so submitting explicitly is not redundant —
without it that purchase is only seen on the next launch, and only if you have
not finished it. Submitting through both paths is safe: the queue deduplicates
on the signature.

### What it does not do

| | |
| --- | --- |
| `transaction.finish()` | **Never called.** Only your app knows whether the entitlement was delivered. |
| Price, currency, product type | Never sent. Apple signs them; the server reads them from the signature. |
| Its own verification verdict | Never used to filter. `.verified` and `.unverified` are both submitted, because the server decides against Apple's root certificates. |
| Advertising identifiers | Never touched, in any target. |
| Your raw account key | **Never written to disk.** The queue stores an identity *epoch*; the raw value is resolved from the core client at delivery, and only if that identity is still current. |

### Signing out, and switching accounts

A purchase queued while User A was signed in is **never** delivered labelled as
User B. `resetIdentity()` and a second `identify(...)` both advance the core's
identity epoch, which permanently unlabels everything queued before it — the
payment is still delivered, with no user attached.

`setConsent(.disabled)` goes further: pending delivery is cancelled and the
stored evidence is deleted before the call returns.

### Where the evidence lives

Unacknowledged signed transactions are written to
`<Application Support>/WebmasterID/<property>/storekit/`, under
`.completeFileProtection` on iOS, tvOS, watchOS and visionOS. This file is
separate from the analytics event queue and has its own bounds.

**Stated plainly:** the raw JWS *is* on the device until the server
acknowledges it. A queue that discarded the signature could not retry, and a
purchase made offline would be lost. It is never persisted server-side.

Because the file is under complete protection, it cannot be read before the
device's first unlock. A background refresh that runs that early sends nothing
and tries again later — nothing is lost, because you have not finished the
transaction and StoreKit re-offers it.

### Connecting a purchase to a user

Set `externalUserID` to your own opaque account key — never an email address,
which is refused outright rather than hashed. When your app also sets Apple's
`appAccountToken` at purchase time, the purchase resolves to the **same**
pseudonymous user as that app's mobile events, and the customer's journey opens.

If you do not set `appAccountToken`, the payment is still recorded in full; it
simply has no user attached, and the server says so with
`missing_app_account_token`.

### Reading the acknowledgement

```swift
let d = await storeKit.diagnostics()
d.lastPaymentOutcome   // .accepted / .duplicate / .rejected
d.lastIdentityOutcome  // .linked / .ambiguous / .retryable / …
d.pending              // evidence still waiting
```

Payment and identity are reported **separately** because they fail
independently: money is durable once Apple's signature verifies, while linking
it to a user can stay unresolved afterwards. Evidence is kept whenever identity
is `retryable`, even though the payment is already banked — dropping it there
would strand that purchase unlinked forever.
